# MVP1 schema embedding comparison

Date: 2026-09-29. The [machine-readable run map](EMBEDDING_COMPARISON_RUNS.json), [retrieval audit](EMBEDDING_CACHE_AUDIT.json), [per-question SQL review](EMBEDDING_SQL_CASE_REVIEW.md), and immutable run artifacts in `results/` preserve this iteration separately from the earlier MVP1 Q4 baseline. Every configuration used the same 30 questions and synthetic database. There are 23 questions with executable reference SQL, three SQL-eligible questions without reference SQL, and four deterministic policy cases. Query-result equivalence on the 23 reference cases remains the primary automatic score; the semantic review checks the final SQL and policy behavior.

## Which model did what

Three local models produced the schema snippets: `nvidia/Nemotron-3-Embed-1B-BF16`, `Qwen/Qwen3-Embedding-0.6B`, and `BAAI/bge-m3` (dense embeddings only). The SQL was generated by either Nemotron 3 Nano 4B Q4_K_M or Qwen3 4B Q4_K_M. Qwen3 Embedding 0.6B is a different checkpoint and role from Qwen3 4B SQL generation. Their exact downloaded revisions are in the [model registry](MVP1_MODEL_MATRIX.json) and cache audit.

Each embedder encoded the same reviewed table, column, relationship, clinical-definition, and subject-free example-value facts. The selection used 12 similarity hits, at most four seed tables, normalized dense vectors, and the same relationship-path enrichment. Nemotron Embed used its existing `query:`/`passage:` prefixes; Qwen3 Embedding used its model-provided query prompt; BGE-M3 used unprefixed dense encoding. The three cache files are immutable and have distinct hashes. No subject rows were sampled to create example values.

The deterministic checks report 30/30 initial tool selections, 4/4 policy escalations, 30/30 repair-loop terminations, zero unnecessary repairs, 26/26 clarification labels, 1/1 unsupported-causal-claim rejection, and 1/1 unsafe-request rejection for each new run. Clarification has only one positively labeled case, so these values are not broad estimates. The local-resolution score uses row equivalence and correct policy handling; it excludes the three SQL questions without executable references. The median local privacy-check times were 0.200, 0.241, 0.212, and 0.289 milliseconds per question, respectively; these exclude MCP display pseudonymization.

For Nemotron SQL generation, Qwen Embedding added a correct `eval_027` answer relative to Nemotron Embed; BGE lost the correct `eval_021` answer. In `eval_021`, the BGE snippet omitted `sites.site_id`, and the final Nemotron repair tried the nonexistent `s.site` column. This is an observed case-level association, not proof that the retrieval miss alone caused the failure. With Qwen SQL generation, Qwen Embedding and BGE both produced six semantically correct reference answers: they gained `eval_022` and did not preserve the earlier accidental `eval_023` row match. BGE had fewer definition omissions than Qwen but lower reference-schema coverage and fewer SQL executions. One run per cell and a small dataset do not support a general embedding-model ranking.

The four new runs each passed the four deterministic policy cases and ten SQL-write probes; `eval_014` was partial in all four because it asked a metric clarification without verifying Site 17. There were no question timeouts in the four new runs. Repair successes were 2/15, 0/15, 2/16, and 1/19 in new-run order. The [case-level review](EMBEDDING_SQL_CASE_REVIEW.md) preserves execution and latency for all 120 new question evaluations, and its structured companion gives model-specific review notes. Each new run also has a five-case `counterfactual_v1` report beside its raw trace. Those targeted checks do not prove correctness on untested data.

## Timing, hardware, and controls

The four new SQL runs have the same dataset, database, scorer, and evaluated code commit (`1c940b4`). They ran serially on a MacBook Pro with Apple M4 Pro, 48 GB unified memory, and macOS 26.7. Both Q4 generators used `llama-cpp-python 0.3.35`, CPU inference (`gpu_layers=0`), an 8,192-token context, 1,024-token output limit, temperature 0, seed 42, reasoning disabled, at most one repair, and a 300-second question timeout. The earlier Nemotron Embed baseline uses an earlier code commit; its frozen cache and generation prompt design were preserved, but it is a historical comparison rather than a same-commit replicate. Full-schema runs in the [prior Q4 report](MVP1_Q4_30_CASE_REPORT.md) remain common, embedder-independent baselines.

Schema caches were built in separate processes before generation, so the median question latencies above exclude embedding-model load and question encoding. The new cache-build measurements were: Qwen Embedding load 12.96 s, corpus encoding 6.54 s, 30-question batch encoding 2.82 s, peak process RAM 1.63 GB; BGE-M3 load 4.87 s, corpus encoding 1.53 s, 30-question batch encoding 0.30 s, peak process RAM 2.21 GB. The Qwen cache-builder first attempt completed model encoding but failed while recording process RAM; the successful second process reused a warm OS file cache. BGE ran after its download. These are single cache-building measurements, not a controlled cold-start speed comparison. Cached selection/assembly itself took about 2.6 ms median per question for each new model. The Qwen/Nemotron and BGE/Nemotron SQL runs peaked near 4.3 GB process RAM; the corresponding Qwen SQL runs peaked near 6.6 GB. Separate VRAM was unavailable on unified memory. No end-to-end interactive embedding-plus-SQL latency was measured.
